Readiness-driven visit planning that cuts wasted trips for families travelling for cancer care.

Solution note — what is built, how it was demonstrated, and how data is handled.

1. The problem, and the mechanism

60%
of Tata Memorial Hospital's ~45,000 new patients a year come from outside Maharashtra [1]
75%+
of gastric and pancreatic cancer patients studied at Tata Memorial travelled over 500 km [2]
83%
faced catastrophic non-medical costs; mean ₹88,433 on travel, lodging and food [2]

The mechanism is the wasted trip. A report is not ready. A consult is booked before the scan it needs. A return date is a guess. Each costs the family days of lodging, food and lost wages. Every department optimises its own queue; nobody counts the family's trips, because that cost appears in no hospital metric.

Saathi plans each visit so a family travels only when the visit can actually happen. One rule: never travel for a step whose prerequisite is not ready.

2. What is built

A working system, not a mock-up: a planner, a language layer, a guard, an evidence ledger, live fact-fetching tools, and two separate applications — one for the family, one for the hospital.

Stack as built

  • Planner — LangGraph over a typed tool registry; FastAPI; server-sent events.
  • Language — Groq gpt-oss-20b, strict structured output; Claude bound identically as an alternate.
  • Speech — Groq whisper-large-v3-turbo; system voices for read-aloud; Bhashini adapter in place.
  • Actors — gpt-oss-120b writes what a caregiver would say: an input, never a decision.
  • Consoles — React 18, Vite, strict TypeScript; three entry points.

Scope and safeguards

Logistics only: status, dates, documents, directions. By design it does not diagnose, recommend treatment, provide clinical decision support, score clinical risk, interpret medical data or give clinical advice. Any clinical question is routed to the care team.

Languages

Hindi, Bengali, Odia and English end to end — verdict, plan, conversation and voice. Choosing a language changes the family's record, not the view.

What is staged, precisely

Only the inputs a human would otherwise supply: which button is pressed, and what the family asks. The spoken question is a synthesised clip presented to the browser as a capture device — from getUserMedia onward nothing knows the difference: a real recorder captures it, the real endpoint receives it, real transcription reads it.

Everything downstream is the system: the planner really re-runs, the routing tools really fetch, the model really writes each message, the guard really reads it, the ledger really grows. Two runs differ in wording because the model's output differs — identical frames every time would mean a video, not a run.

One limitation stated plainly: the screen recorder captures no audio track, so the read-aloud is visible in the film but not audible. It works; a live run is audible.

5. How data is handled

No clinical content ever enters the system

The ABDM ingest drops conclusion, presentedForm and result at the boundary. The internal pointer type has no field that could hold a finding. The family-facing endpoint has a closed key set — timing and status only — asserted by a test that fails if anyone adds a field to it. Saathi reads that a report exists and whether it is ready; it never reads what the report says.

Every claim names its source, and the record cannot be quietly edited

The evidence ledger is append-only and hash-chained, so a claim cannot be altered after a family has acted on it. It grows only when a fact changes, so a patient re-planned every simulated day does not bury the one entry that asserts something new. The console displays chain integrity from a real verification, not a badge.

Fetched facts carry provenance; hospital policy is owned by the hospital

Distances and journey times come from live routing and geocoding services and arrive with a source URL, a fetch time and a response hash. Facts about the hospital — lead times, slot rules, shift tolerances — are administrator-owned configuration that ships marked unconfirmed, so nobody mistakes a default for the hospital's policy.

A booking is a fact; a forecast is a range

A date the hospital has committed to is shown as one date and called confirmed. A prediction is shown as a calibrated interval and never dressed up as a promise. Where there are too few comparable cases to stand behind an interval, no interval is shown — a range the system cannot defend is worse than none.

Consent is enforced at the point of reading, and refusals are logged

Grants are scoped per record pointer and checked when data is read, not when it is requested. An access attempt without a grant is recorded as an attempt rather than silently dropped. The model follows the DPDP Act 2023 and ABDM consent artefacts.

The record is not retroactively tidied

Changing language changes what is written from that moment on. Past messages keep the language they were actually sent in and are labelled accordingly, because that thread is the only record of what the family was told. A no-op change costs neither a ledger row nor an API call.

The guard fails closed

A message that cannot be validated against the plan it came from is never sent. The family's screen says a person will call, rather than substituting text nobody approved. Outbound validation includes checking that the planned date is positively present in the message, in that language's own numerals.

Reading causes nothing

Opening a family's page does not plan, re-render or write. Ordering in the worklist follows from two visible facts — whether a decision is waiting, and how far the family would travel — not from a priority score; there is no field that could hold one.

Operational posture

  • No credentials in the test path. The suite blanks and then asserts the absence of API keys, proving the decision path never depends on an external service. If the network dies mid-demo, the planner, the guard and the ledger still work; only the wording falls back to templates.
  • Synthetic patients throughout. No real patient data exists anywhere in the prototype. Pilot data would arrive via live ABDM and one hospital's status feed.
  • Secrets stay out of the repository. API keys live in an ignored environment file and are never printed.

6. How we will measure it

  • Wasted trips avoided
  • Days the family spends in the city
  • Non-medical out-of-pocket cost avoided (₹)
  • Dropout after the first visit

Prototype: synthetic patients with planted ground truth, so every claim the planner makes can be scored against what was actually true. Pilot: live ABDM data and one hospital's status feed, with the same scoring harness.
